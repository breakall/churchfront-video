# Churchfront Video: Canon controller handoff research

Current requirements are maintained in [camera-control-settings.md](camera-control-settings.md). The user has clarified that manual takeover disables tracking until an explicit new start, that native tracking interception is optional, and that preset buttons must not be repurposed. Earlier proposals for automatic resume or a manual-mode button are superseded.

Inspected 2026-11-23. Public `main` commit: `9892525d2a624af82c5fb8eaed6655179472b399`. This is a source review; no physical CR-N500/RC-IP100 test was performed. An installed build may differ.

## What the project says

The README explicitly names RC-IP100 among controllers that can compete with Churchfront for a Canon session, producing a “waiting for control” warning. It advises closing the other controller. This describes the project's present design and observed problem, but should not be generalized into an unavoidable Canon hardware limitation: Canon's own protocol document contains an important exception described below. [README, lines 125–130](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/README.md#L125-L130)

## Exact connection behavior

- Canon mode (`canonXC`, shown as “Canon (HTTP)”) uses HTTP port 80 and the `/-wvhttp-01-/` API. VISCA UDP and TCP are separate options. [PTZ.swift, lines 5–26](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L5-L26)
- A Canon link opens `open.cgi`, saves a session ID, calls `claim.cgi`, and reports whether `s.control` starts with `enabled`. It retries claiming every 1.5 seconds while waiting, and its normal keepalive calls claim every 10 seconds. Thus turning tracking off does not prevent the app continuing to claim camera control. [PTZ.swift, lines 640–709](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L640-L709)
- Motion requests use `control.cgi?s=<session>&...`. Failed commands clear pending motion, retain stop commands for retry, and claim again. [PTZ.swift, lines 782–819](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L782-L819)
- Nuance: `pump()` does **not** refuse commands when `hasControl == false`; it checks session existence. Manual UI controls are also not disabled by `hasControl`; that flag produces a warning. A patch that merely ignores the flag is therefore unlikely to solve this. [PTZ.swift, lines 794–801](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L794-L801), [VolunteerView.swift, lines 290–305](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/VolunteerView.swift#L290-L305)
- `CanonLink.stop()` cancels its timer and calls `close.cgi`, but is not exposed as a user-facing per-camera manual-control handoff. Links are stopped/rebuilt when camera connection configuration changes. [PTZ.swift, lines 651–658](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L651-L658), [PTZ.swift, lines 985–1008](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L985-L1008)

## Tracking handoff actually available

- The Track button toggles tracking on the camera on Next. Clicking a person in the preview starts/restarts tracking on that person. [VolunteerView.swift, lines 120–132](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/VolunteerView.swift#L120-L132), [lines 696–721](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/VolunteerView.swift#L696-L721)
- Command-T toggles tracking on Next; Command-period stops all tracking. These Camera-menu actions are disabled outside Operator view. [App.swift, lines 220–240](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/App.swift#L220-L240)
- The app's own manual pan/tilt, shot, preset or home action invokes a callback stopping tracking. This is an internal app callback; there is no corresponding RC-IP100 joystick listener in the inspected code. Manual zoom in the app instead keeps tracking. [Tracker.swift, lines 195–200](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/Tracker.swift#L195-L200), [PTZ.swift, lines 1028–1041](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L1028-L1041)
- `AutoTracker.stop()` removes tracking sessions/frame subscriptions, sends movement stops if needed, and stops its timer when no sessions remain. It does **not** yield, close or otherwise change the Canon control session. Consequently “Stop tracking, move RC-IP100, resume” is the intended operator sequence but is not a verified workaround for the user's connection conflict. [Tracker.swift, lines 255–268](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/Tracker.swift#L255-L268)
- When a subject disappears, the tracker holds camera movement and enters searching/lost states; it attempts appearance-based reacquisition. That does not mean it releases the Canon control session. [Tracker.swift, lines 411–446](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/Tracker.swift#L411-L446)

## Automation / Companion

The app exposes a localhost-only HTTP API at `127.0.0.1:9911`: `POST /call` with `{"name":"stop_tracking","arguments":{"camera":"Camera name"}}` or `start_tracking`. Requests need `X-CueVideo-Token` using the locally stored control-token. This can be called by software running on that same Mac, including a generic HTTP integration or small local bridge. No dedicated Companion integration or release/yield camera tool was found. A stop/start button alone cannot fix control-session contention. [ControlServer.swift, lines 4–12](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/ControlServer.swift#L4-L12), [lines 104–119](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/ControlServer.swift#L104-L119), [ControlTools.swift, lines 268–278](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/ControlTools.swift#L268-L278), [lines 352–355](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/ControlTools.swift#L352-L355)

API `start_tracking` normally refuses an on-air camera unless `allow_live: true` is explicitly supplied. Camera identifiers accept configured name, IP or ATEM input number. [ControlTools.swift, lines 535–551](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/ControlTools.swift#L535-L551)

## Canon protocol nuance and likely development paths

Canon's XC Control Protocol Specifications, BPE-7216-005, section 1.1.1 (printed page 1 / PDF page 7), says ordinary remote-camera control generally need not use a session and control rights do not restrict control; camera-side user-right restrictions remain relevant. Its supported models include CR-N500. This conflicts with a blanket statement that the camera can never be used by multiple controllers. It does not establish that the user's installed firmware/settings or RC-IP100 behavior will interoperate correctly without testing. [Canon-authored protocol specification](https://output.nl/u/images/canon-xc-control-protocol-specifications-005.pdf#page=7)

Two plausible engineering routes, both requiring bench validation:

1. Keep Canon HTTP but use sessionless CR-N500 movement commands where supported; add explicit Manual/Tracking mode so the app sends no tracking movement while the physical operator recovers the subject. Retain session handling for operations that require it. Do not blindly remove all session code across all Canon models.
2. Use VISCA-over-IP control while RC-IP100 remains on Canon's protocol, **if Canon's current CR-N500 documentation confirms simultaneous interoperability**. App supports VISCA, but changing protocol changes its preview routing: non-Canon mode requires an NDI picture mapped to the camera's ATEM input. It will no longer automatically take the Canon HTTP preview. [CameraPicture.swift, lines 5–15](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/CameraPicture.swift#L5-L15)

Do not promise that selecting another protocol is a complete solution until preview availability, motion units, firmware support and controller coexistence have been checked on this hardware.

### VISCA tracking calibration detail

The current app allows Track for a VISCA camera with an NDI picture; the button's only relevant enablement condition is `CameraPicture.of(camera) != nil`. [VolunteerView.swift, line 721](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/VolunteerView.swift#L721)

However, all `VISCALink` instances currently use `VISCAUnits.ptzOptics`, with 14.4 position counts per degree, a 58-degree wide horizontal FOV, 20x lens model and zoom maximum 16384. There is no Canon-specific VISCA calibration selector in this code. The position and FOV the tracker sees will therefore follow these assumptions; pan/tilt speed conversion is also generic. This is a material limitation of recommending VISCA on the CR-N500: basic control and NDI tracking may function, while framing/speed/zoom accuracy must be tested. [PTZ.swift, lines 250–275](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L250-L275), [line 305](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L305), [lines 412–414](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L412-L414), [lines 452–456](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L452-L456)


## Practical recommendation for this system

The evidence supports an application control-session conflict, but the physical setup and installed app version remain untested. The ATEM is not part of Churchfront's Canon HTTP connection: the app drives camera IP directly. Start with a rehearsal comparison: stop tracking (Command-period in Operator view), test the RC-IP100, then quit Churchfront and test again. A controller that only recovers after quitting supports the session-contention diagnosis; it does not isolate every camera or network setting. [App camera controls](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueVideo/App.swift#L220-L240), [Canon connection implementation](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L640-L709)

For retaining Churchfront tracking, request an explicit per-camera Manual/Tracking handoff. Proposed behavior (not implemented): Manual stops and drains tracking movement, suppresses all automatic control claims/reconnects and camera movement writes for that camera, and yields/closes its control session. Tracking explicitly reacquires control (with an actionable error if RC-IP100 still holds it) and uses a fresh target selection. Evaluate sessionless XC for normal CR-N500 control to avoid continuing session contention. Handling the RC-IP100's own control claims must be part of bench validation; an app-side release alone does not prove successful takeover in the reverse direction. The desired operator sequence is: Manual, physically reframe, release joystick, explicitly select person/resume Tracking. Automatic takeover on physical joystick movement is a separate feature requiring an observable controller signal, not just camera position changes.

A no-code VISCA-over-IP experiment can avoid Churchfront's Canon session path, but should not be represented as a verified solution. It needs an NDI preview mapped to the camera's switcher input. The current VISCA link always uses the PTZOptics calibration (14.4 counts/degree, 16384 zoom steps, 58-degree wide field of view, 20x zoom), so tracking on a CR-N500 can be miscalibrated. [PTZ.swift](https://github.com/Churchfront/churchfront-video/blob/9892525d2a624af82c5fb8eaed6655179472b399/Sources/CueATEM/PTZ.swift#L259-L305)

A manufacturer-supported alternative is Canon's RA-AT001 tracking application on the CR-N500. Canon documents CR-N500 compatibility and a 30-day trial, and RC-IP100 firmware 1.40 adds control of RA-AT001. The controller manual exposes Auto Tracking start/stop under FUNC. This allows a workflow using Canon tracking start/stop and the physical joystick, rather than Churchfront's tracker. Churchfront must cease its competing Canon connection if it is still used for ATEM switching. Check installed versions and current licensing before deployment. [Canon CR-N500 tracking support/trial](https://www.usa.canon.com/support/canon-product-advisories/Software-Notice-Auto-Tracking-Application-RA-AT001-Software-Version-1-1-0), [RC-IP100 firmware support](https://sg.canon/en/support/0400911702), [Canon-authored RC-IP100 manual, mirror](https://manuals.plus/m/953f8e847f962cba76ab9a70fb79c8577fd89e301eaf35fa88de7beeace18256)
