## Offline hardening on the Mac mini, 2026-11-27

The camera and RC-IP100 were offline during the simulator checks. The current branch was built as a native Apple silicon release using the Mac's full Xcode toolchain. The app's deep/strict signature check, embedded plists and packaged font resource check passed. No production bridge profile or loaded production service was present; production configuration and registration remain pending the equipment setup.

An additional fault scenario reproduced a handoff gap: a malformed controller information response revoked tracking authorization but left the camera's last app-owned movement running. Information-stream failures now request an app-axis stop through the existing serialized, generation-fenced writer. Physical axes are excluded, a later physical takeover invalidates queued cleanup, and an unconfirmed stop blocks tracking restart. This change affects movement ownership.

A delayed camera reply also exposed a controller ownership race. Queued moves and stops could execute after the same local session yielded and reclaimed control. The writer now checks the original claim before sending a physical action. Recovery checks the claim associated with a release before clearing a held joystick. A rejected takeover also allows the bridge to stop any outstanding app-owned pan. Two simulator regressions cover these transitions, and the lifecycle scenario exercises local session priority updates and queries.

The operator workflow starts with Churchfront following a person. The first physical PTZ input takes control whether the tracker is still following or has lost sight of that person. The operator frames the intended person and releases pan, tilt and zoom. Tracking stays off until the operator presses Track in Churchfront. A normal Track press uses the new picture and picks the person at or nearest the center. In the Next preview, clicking a person selects them explicitly when people stand close together.

The Churchfront side of the RC-IP100 tracking button is wired. A loopback test sends simulated Start and Stop presses through the controller listener and observes the real Churchfront tracker and every request at the fake camera. Recognized presses are consumed locally with interception enabled. A Start while the joystick is held is declined immediately. Releasing the joystick then pressing Start creates a fresh tracking run. Stop cancels an overlapping Start and settles any app-owned camera motion. With interception disabled, the same test commands pass through. On the equipment, capture the menu capability check, Start, Stop and status refresh, map the verified requests, then check the controller indicator against the tracker state reported by the app.

Both workflows exposed an app race in offline tests with synthetic person detections. A detection from the previous run could arrive after Track and reacquire the old person. Each tracking run now accepts only its own detection and position callbacks. Its preview subscription waits for the next published frame. The tests cover takeover from both following and lost, including when the previous person remains visible off-center in the new framing.

Seven reconnect scenarios drop the controller TCP connections with the joystick held and open a new local session while an old move or stop is outstanding. In the simulator, a pan already in motion continues through disconnect. On takeover, the bridge discards old queued actions, including writes without a session ID. A delayed old stop can leave the camera stationary, but its reply cannot release pan for the new owner. If a write times out with execution uncertain, the helper confirms closure or expiry of the old camera session, claims a replacement camera session and confirms a recovery stop before forwarding fresh movement. If closure fails, input during recovery is rejected and must be sent again. The new owner must release the held axis before an explicit tracking restart.

## Checkpoint status

This branch contains work in progress from equipment testing on the Mac. The native helper owns and renews one Canon camera session. The RC-IP100 receives a separate local session. Its open, claim, yield, close and session requests terminate at the bridge. Physical input revokes tracking and takes priority. Camera session loss invalidates queued movement and requires a confirmed stop after reconnection. Tracking requires explicit reactivation.

Other changes include bounded, sanitized diagnostics, recovery from Canon status headers containing descriptive text, autofocus-aware startup recovery, automatic helper re-registration after an update, and controller status translation for fixed, chunked and multipart responses. Sessionless discovery preserves original fixed-length camera response bytes when translation is unnecessary.

```sh

CAMERA_BRIDGE_TEST_BINARY="$PWD/Churchfront Video.app/Contents/Helpers/camera-control-bridge" PYTHONPATH=Tools python3 -m unittest discover -s Tools/camera_rig/tests
```
